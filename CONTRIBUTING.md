# Contributing

Thanks for helping make CI failures less painful. The most valuable contribution is a **new known-failure entry** for a failure you've debugged.

## Add a known-failure entry

1. Pick the file: `skills/ci-failure-explainer/references/stack-<stack>.md`, `stack-general.md` for platform or runner issues, or `flaky-tests.md`.
2. Use the next free ID for that file (`NODE-19`, `PY-17`, …). IDs are permanent: never renumber.
3. Follow the format exactly:

   ```markdown
   ### NODE-19 · Short, searchable name
   - **Signature:** `first regex` · `second regex`
   - **Category:** dependency
   - **Cause:** Why it happens, in 1–2 lines.
   - **Fix:** The proven fix. Short snippet if helpful.
   - **Verify:** `the command that proves it's fixed`
   ```

   Categories: `build`, `test`, `lint`, `dependency`, `config`, `permissions`, `infrastructure`, `flaky`.

4. Validate: `python3 skills/ci-failure-explainer/scripts/match_patterns.py --validate`
5. Add a real-looking excerpt to `REPRESENTATIVE` in `tests/test_match_patterns.py`, so the entry must keep ranking first through the real digest.
6. Check it on a real log: `clean_logs.py failed.log > digest.md && match_patterns.py digest.md --explain NODE-19` shows which signatures hit, the root-cause bonus and the rank. If another entry wins, the output says which.

### Writing good signatures

- Signatures are **Python regexes**, matched line by line against the *cleaned* log (timestamps, ANSI codes and `gh` prefixes are already stripped). They're **case-sensitive**. Prefix with `(?i)` if needed.
- Prefer the tool's exact, stable wording (`ERR_PNPM_OUTDATED_LOCKFILE`) over generic words (`error`). Specific signatures score higher: the matcher weights each hit by how much literal text it pins down.
- A backtick can't appear inside a signature (it ends the code span). Use `.` to match it.
- Strip variable parts: `\S+` for names and paths, `\d+` for numbers.
- 2–4 signatures per entry is ideal: the headline error plus a distinctive secondary line.
- No nested unbounded repeats such as `(\S+\s?)+` or `(.*,)+`. Logs are hostile input, and these can backtrack for minutes, so `--validate` rejects them. `(\.\w+)*` is fine: every iteration starts with a character `\w` can't match.
- Avoid umbrella messages as signatures ("Your lock file does not contain a compatible set of packages"). Their long literal text scores high, but the reason is on the lines below them.
- Never paste real secrets, internal hostnames or proprietary log lines.

## Add a test fixture

Fixtures are synthetic and generated by `tests/fixtures/generate_fixtures.py`, so they stay reviewable and reproducible.

1. Add a builder function that writes a realistic, noisy log (use the existing noise helpers). `Log(..., prefixed=False)` writes a full GitHub job log, `Log(..., stamp="none")` with `log.section()` a GitLab trace, and `Log(..., stamp="bracket")` a Jenkins console log with timestamper prefixes.
2. Register it in `main()` and add an `EXPECTED` entry (`must_contain`, `pattern`, `category`, `stack`, `root_cause`, `fix`).
3. Run `python3 tests/fixtures/generate_fixtures.py`, then `python3 -m unittest discover tests` and `python3 tests/run_eval.py --write`.

## Code changes

- Python 3.9+ and the **standard library only**. No third-party imports, ever.
- Type hints and short comments where the logic isn't obvious. Every script keeps `--help`, clear errors and non-zero exit codes.
- Redaction changes need a test in `tests/test_clean_logs.py` proving no secret leaks.
- Run the full suite before opening a PR:

  ```bash
  python3 -m unittest discover tests && python3 tests/run_eval.py && \
  python3 skills/ci-failure-explainer/scripts/match_patterns.py --validate
  ```
